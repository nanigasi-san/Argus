# Argus リリース後改善計画

作成日: 2026-08-04  
調査対象: `main` / `be8a553` / `0.6.0+1008`

## 1. 目的

リリース後の Argus を、安全性と保守性を落とさず継続的に改善するための実行計画をまとめる。

本書では、改善候補を次の3種類に分ける。

- **潜在不具合**: 現在の実装から故障経路を確認できるが、実機での再現確認が必要なもの。
- **信頼性改善**: 現在動作していても、長時間運用や OS・プラグイン失敗に弱いもの。
- **リファクタリング**: 外部挙動を変えず、変更影響とテスト負担を小さくするもの。

安全機能であるため、リファクタリングより先に「警告を開始・継続・停止できること」と「位置判定を順番どおり処理すること」を優先する。

## 4. P0: 最初に修正する項目

### 4.1 位置イベントを必ず受信順に処理する

#### 現状とリスク

`AppController.startMonitoring()` は位置ストリームの各値を `unawaited(_handleFix(...))` で処理している。`_handleFix()` 内にはログ、通知、バイブなど複数の非同期処理があるため、後から受信した測位の処理が先に完了する可能性がある。

同じ監視 run 内の処理順は `_monitoringRunId` では保護されない。その結果、古い OUTER 判定が新しい INNER 判定を上書きする、復帰通知と離脱通知が逆順になる、といった競合が起こり得る。

また、`AppController` と `GeolocatorLocationService` の `listen()` に `onError` / `onDone` がなく、開始後の位置ストリーム異常を UI とログへ確実に反映できない。

#### 改善案

- `MonitoringSession` を追加し、1 run につき位置情報を直列キューで処理する。
- 新しい位置情報を「全件処理」「最新値のみ保持」のどちらにするか仕様化する。状態ヒステリシスを守るため、既定は全件・受信順処理とする。
- ストリームの `onError` / `onDone` を監視し、購読解除、警告停止、エラー表示、ログ記録を1つの終了処理へ集約する。
- `startMonitoring()` の多重呼び出しを冪等化し、開始中・監視中・停止中を型付き状態で管理する。

#### 受け入れ条件

- 1件目だけログまたは通知を意図的に遅延させても、2件目が追い越さないテストがある。
- `OUTER → INNER` を短時間に投入しても最終状態と警告状態が必ず INNER になる。
- ストリーム error / done 後に UI が監視中のまま残らない。
- 停止後に処理中だった測位が状態・通知・ログを更新しない。

対象: `lib/app_controller.dart`, `lib/platform/location_service.dart`, `test/app_controller_test.dart`, `test/platform/location_service_test.dart`

### 4.2 通知・警告音・バイブを独立したフェイルセーフ処理にする

#### 現状とリスク

`Notifier.notifyOuter()` はローカル通知の表示後に警告音を開始する。通知プラグインが失敗すると、より重要な警告音とバイブまで開始されない。

反対に `dismissOuterAlert()` は通知初期化・通知キャンセル後に警告音とバイブを停止する。通知処理が失敗すると停止処理へ到達しない。`stopAlarm()` も先の停止処理が例外になると後続リソースを停止できない。

#### 改善案

- 通知、警告音、バイブを独立して実行し、1チャネルの失敗で他チャネルを中断しない。
- OUTERでは警告音・バイブ開始を優先し、通知は失敗しても警告全体を失敗扱いにしない。
- 停止は各チャネルを `try/finally` 相当で必ず試行し、複数エラーをまとめてログへ残す。
- `AlertOperationResult` のような型でチャネル別の成功・失敗を返し、Controllerがユーザー向けメッセージを決める。
- 再開、スヌーズ、アプリ復帰、プレビューを同じ `AlertCoordinator` の状態機械へ統合する。

#### 受け入れ条件

- 通知表示が失敗しても警告音とバイブが開始される。
- 通知キャンセル、警告音停止、バイブ停止のどれかが失敗しても、残りの停止処理は実行される。
- 開始中に停止された場合、遅れて開始完了しても警告が残らない。
- スヌーズ中、復帰後、アプリ resume 後の状態が単一のテスト表で網羅される。

対象: `lib/platform/notifier.dart`, `lib/app_controller.dart`, `test/platform/notifier_test.dart`

### 4.3 監視開始の安全条件を Controller 内で一元化する

#### 現状とリスク

Android のアラーム音量50%以上という確認は `canStartWithCurrentAlarmVolume()` と Home UI の協調に依存する。`startMonitoring()` 自体はこの条件を確認しないため、新しい画面、テスト用導線、将来の自動再開から直接呼ぶと確認を迂回できる。

#### 改善案

- `MonitoringStartGuard` を作り、GeoJSON、位置権限、位置サービス、Androidアラーム音量、開始中かどうかを一括評価する。
- `startMonitoring()` は `MonitoringStartResult` を返し、成功、権限不足、低音量、位置サービス無効、プラットフォームエラーを型で区別する。
- UI は結果に応じた表示だけを担当し、安全条件の判断を持たない。
- 音量取得失敗時に開始を許可する現仕様は維持するが、warning と診断情報を必ず残す。

#### 受け入れ条件

- `startMonitoring()` を直接呼んでも Android 低音量時は開始されない。
- Home以外の呼び出し元でも同じ開始結果になる。
- 開始ボタンの連打で位置ストリームが重複購読されない。

対象: `lib/app_controller.dart`, `lib/ui/home_page.dart`, `test/app_controller_test.dart`, `test/ui/home_page_test.dart`

### 4.4 未対応GeoJSONを黙って受け入れない

#### 現状とリスク

`GeoModel.fromGeoJson()` は Polygon / MultiPolygon の最初のリングだけを読み込み、内側リング（穴）を無視する。穴が立入禁止・監視対象外を表すデータでは、その領域を安全エリアとして扱う可能性がある。

型キャスト中心のパースで、FeatureCollection、座標の有限性、緯度経度範囲、リング構造を明示的に検証していない箇所もある。安全機能では「一部だけ解釈して成功」にするより、未対応形式を明示的に拒否する方が安全である。

#### 改善案

短期対応:

- 穴を含む Polygon / MultiPolygon をユーザー向けエラーで拒否する。
- ルート型、features、geometry、座標数、有限値、緯度 `-90..90`、経度 `-180..180` を検証する。
- 無効な Feature を黙って無視せず、どの Feature が不正かを返す。
- 読み込み前にファイルサイズ、Feature数、頂点数の上限を設ける。

中期対応:

- 利用要件がある場合は `GeoPolygon` を外周と内周の集合へ拡張し、包含判定、距離、QR仕様を同時に更新する。

#### 受け入れ条件

- 穴を含むGeoJSONが成功扱いにならない。
- `NaN`、無限値、範囲外座標、短すぎるリング、想定外のルート型が明確な検証エラーになる。
- エラー時に既存の監視エリアと監視状態が失われない。

対象: `lib/geo/geo_model.dart`, `lib/geo/point_in_polygon.dart`, `lib/qr/geojson_qr_codec.dart`, `test/geo/geo_model_test.dart`

## 5. P1: 次に行う信頼性改善

### 5.1 GeoJSON読込を二段階コミットにする

現在はファイルピッカーやQR画像ピッカーを開く前に `stopMonitoring()` を呼ぶため、ユーザーがキャンセルしただけでも監視が停止する。

次の順に変更する。

1. 選択・読込・検証・インデックス構築を一時オブジェクト上で行う。
2. 成功した場合だけ監視を停止する。
3. 新しいGeoJSON、表示名、一時ファイルをまとめて反映する。
4. 反映失敗時は以前のエリアと監視状態へ戻す。

大きなGeoJSONのパースとインデックス構築は isolate へ移し、UI停止を防ぐ。選択キャンセル、パース失敗、ファイル書込失敗のいずれでも既存監視を継続できることをテストする。

対象: `lib/app_controller.dart`, `lib/io/file_manager.dart`, `test/app_controller_test.dart`

### 5.2 設定保存をトランザクション化する

`updateConfig()` は監視を停止し、メモリ上の設定を更新してからファイル保存する。保存失敗時は新旧設定が混在し、監視も停止したままになる可能性がある。

- 一時ファイルへ書き込み後、置換する方式で `config.json` を原子的に保存する。
- 保存成功後にメモリと StateMachine へ反映する。
- 監視再開失敗を保存失敗と分けて表示する。
- 旧設定・旧監視状態へ戻せるようにする。

対象: `lib/app_controller.dart`, `lib/io/file_manager.dart`, `lib/ui/settings_page.dart`

### 5.3 EventLoggerを長時間運用向けにする

`EventLogger` は各測位で location と state の2レコードをメモリに無制限追加する。3秒間隔なら最大で1日約57,600レコードとなり、長時間監視でメモリ使用量が増え続ける。また、`logStateChange()` は状態が変化していない測位でも毎回呼ばれている。

- メモリ保持件数に上限を設ける。
- state は本当に状態が変わったときだけ記録し、継続サンプルは必要に応じて間引く。
- 永続化が必要ならサイズ上限付きローテーションファイルにする。
- `exportJsonl()` は現在JSON配列を返すため、名前を `exportJson()` に直すか、1行1JSONのJSONLへ実装を合わせる。
- `StreamController` とログ資源に `dispose()` を追加する。

位置情報は機微情報である。エクスポート時の明示確認、保持期間、全削除、緯度経度の丸めまたは診断用匿名化を仕様化し、プライバシー資料と一致させる。

対象: `lib/io/logger.dart`, `lib/app_controller.dart`, `lib/ui/settings_page.dart`, `privacy.md`

### 5.4 OUTER時の距離・方位を実境界から計算する

点が全ポリゴンのバウンディングボックス外にある場合、現在は最も近いバウンディングボックス上の点を距離・方位として使用する。凹形状や斜めの辺では、実際の最寄りポリゴン境界と方向がずれる可能性がある。

AreaIndexは候補絞り込みだけに使い、表示する最終距離・方位は候補ポリゴンの実辺から計算する。多数ポリゴンでの性能を保つため、バウンディングボックス距離で上位候補を選んでから正確な最近傍計算を行う。

受け入れテストには、凹ポリゴン、細長い斜めポリゴン、複数ポリゴン、遠距離点を含める。

対象: `lib/state_machine/state_machine.dart`, `lib/geo/area_index.dart`, `lib/geo/point_in_polygon.dart`

### 5.5 終了イベントに依存しない一時ファイル管理

`AppLifecycleState.detached` から開始した非同期クリーンアップは、プロセス終了までに完了する保証がない。

- 起動時に命名規則と保存先を限定して古い `temp_geojson_*.geojson` を清掃する。
- 一時ファイルは作成成功後に追跡し、置換失敗時も回収できるようにする。
- 終了時清掃は補助扱いとし、正しさを依存させない。
- 通常のGeoJSON読込成功後に、不要になったQR一時ファイルも削除する。

対象: `lib/app_controller.dart`, `lib/io/file_manager.dart`, `lib/main.dart`

## 6. P2: リファクタリング案

### 6.1 AppControllerをユースケース単位に分ける

`AppController` は UI が購読する読み取り状態と、各ユースケースの調停だけに縮小する。

| 分割先 | 責務 |
| --- | --- |
| `MonitoringSession` | 位置ストリーム開始・直列処理・停止・エラー・run管理 |
| `MonitoringStartGuard` | 権限、位置サービス、音量、GeoJSONの開始条件 |
| `GeoJsonRepository` | ファイル/QR読込、検証、一時ファイル、二段階コミット |
| `AlertCoordinator` | OUTER、復帰、再開、スヌーズ、プレビュー |
| `DiagnosticsStore` | UIログ、イベントログ、保持上限、エクスポート |
| `AppController` | 公開状態の集約とユースケース呼び出し |

分割は一度に行わず、P0/P1の修正で新しい境界が必要になった箇所から抽出する。各PRで外部挙動を固定するcharacterization testを先に追加する。

### 6.2 Notifierをプラットフォーム機能別に分ける

`notifier.dart` には通知、警告音、バイブ、音量、MethodChannel実装が同居している。次の単位へ分ける。

- `visual_notification_service.dart`
- `alarm_player.dart`
- `vibration_player.dart`
- `alarm_volume_service.dart`
- `alert_coordinator.dart`

チャンネルID、通知ID、文言は `AlertContract` のような1か所へ集約し、Dart / Android / iOS / テストの重複を減らす。

### 6.3 大きな画面を表示単位へ分ける

- Home: 状態表示、監視操作、ファイル操作、OUTER操作、診断ログ、メニューへ分割する。
- Settings: 設定フォーム、権限カード、アラーム確認、診断情報、アプリ情報へ分割する。
- ビジネス判断は Widget から Controller / use case に移す。
- 画面全体を再構築せず、必要な状態だけを `Selector` 等で購読する。

Widget分割の目的は行数削減ではなく、1つの変更で影響するテストと状態を限定することである。

### 6.4 QR codecを形式別に分ける

`geojson_qr_codec.dart` を次の責務へ分割する。

- GeoJSON構造検証
- `agz1` / `a3` codec
- `gjz1`互換codec
- gzip / Base64URL envelope
- QR容量判定とPNG生成
- ファイル名サニタイズ

既存の公開APIと例外型をfacadeで維持し、分割中に互換性を壊さない。

## 7. CI・テスト・依存更新

### 7.1 CIの改善

- Flutter `stable` の追従だけに依存せず、リリースで使うFlutterバージョンを固定する。
- 現在レポート表示のみのカバレッジに下限ゲートを追加する。ただし100%という数字だけでなく、P0故障シナリオを必須テストにする。
- Androidで `flutter build apk --debug` または同等のビルド確認を追加する。
- Androidネイティブの警告音、AudioFocus、MethodChannelをKotlin側で直接検証する。現在のDart契約テストとソース文字列検査を補完する。
- iOS XCTestを、リソース・Info.plist確認だけでなく音声割込み後の再開や停止の冪等性まで拡張する。
- 実機smokeはPRごとに必須化せず、リリース候補・夜間・手動workflowで実行する。

### 7.2 実機回帰マトリクス

最低限、Android 2機種以上とiPhone 2世代以上で次を確認する。

- 画面ロック、他アプリ前面、長時間バックグラウンド
- 位置権限・通知権限の途中取消し
- 位置サービスOFF/ON、機内モード、省電力モード
- 着信、音声再生、AudioFocus、サイレントモード
- OUTER中のアプリresume、スヌーズ、監視停止、プロセス終了
- 2時間以上のsoak testとバッテリー消費
- GPSが飛ぶ、時刻が前後する、同一点が連続する、精度が急変するケース

実機試験では「警告したか」だけでなく、検知時刻、通知時刻、音声開始時刻、復帰時刻、停止結果を記録する。

現在はルートの `spec.md` と `docs/spec.md` に重複があり、設定項目やバージョン記述に差がある。例えば現行 `AppConfig` の警告音量既定値は0.5だが、古い記述が残っている箇所がある。

- 現行仕様の正本を `docs/spec.md` に一本化する。
- ルート `spec.md` は概要と正本へのリンクだけにする。
- バージョン番号を固定文字列で検査するテストをやめ、`pubspec.yaml` を単一の情報源にする。
- リリース時に仕様、権限文言、プライバシー、ストア審査資料の更新チェックを行う。
- 「実装済み仕様」「既知の制約」「改善予定」を同じ文書内で混ぜない。

## 10. 各PRの共通完了条件

- バグ修正PRには、修正前に失敗する再現テストを追加する。
- リファクタリングPRでは、仕様変更と依存更新を同時に行わない。
- `flutter analyze`、`flutter test`、coverage下限を通す。
- Android / iOS契約に触れる場合は、対象プラットフォームのbuildまたはnative testを通す。
- 位置情報、権限、通知、アラーム、GeoJSON仕様に変更があれば `docs/spec.md` とテストを同時更新する。
- ユーザーに見える失敗は、次に取るべき操作が分かる日本語で表示する。
- 監視停止や警告停止は冪等であり、途中失敗しても再実行できる。
